# PlanPill — Data Schema

โครงสร้างข้อมูลของ PlanPill แบ่งเป็น 2 ไฟล์ที่ต้องแก้ให้ตรงกันเสมอ

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `schema.sql` + `migrate-*.sql` | รันใน Supabase Dashboard > SQL Editor ตามลำดับด้านล่าง |
| `../types.ts` | TypeScript types ของฝั่งแอป อยู่ที่ root ของโฟลเดอร์ `Plan Pill/` |

> เดิมไฟล์ `types.ts` เคยมีสำเนาอยู่ในโฟลเดอร์นี้ด้วย แต่ถูกลบทิ้งเพื่อไม่ให้มี 2 ชุด
> ที่หลุดจากกันได้ ตัวจริงอยู่ที่ `Plan Pill/types.ts` เท่านั้น
>
> `schema.dbml` เป็นสำเนาสำหรับวาดแผนผังใน [dbdiagram.io](https://dbdiagram.io) เท่านั้น
> ไม่ได้ใช้รันจริง แต่ต้องแก้ให้ตรงทุกครั้งที่เพิ่ม migration

## ลำดับการติดตั้ง

1. สร้างโปรเจกต์ใหม่ใน Supabase
2. ปิด **Confirm email** ที่ Authentication > Sign In / Providers > Email
3. เปิด **SQL Editor** แล้วรันไฟล์ตามลำดับในหัวข้อ [รันใน Supabase SQL Editor ตามลำดับ](#3-รันใน-supabase-sql-editor-ตามลำดับ)

ไม่ต้องสร้าง bucket รูปอาหารเอง `migrate-04-storage.sql` สร้างให้พร้อม policy แล้ว

## สิ่งที่พบจากข้อมูลจริง (ตรวจแล้ว)

**ไฟล์ drug-drug ไม่มีคำอธิบายเลย** มีแค่ 5 คอลัมน์ `DDInterID_A, Drug_A, DDInterID_B, Drug_B, Level`
จึงต้องแก้ `mechanism_th`/`management_th` ให้เป็น null ได้ (ทำใน migration แล้ว)

**ไฟล์ drug-food มีครบ** ทั้ง Description, Management, Mechanism — แต่ข้อความ
**ถูกตัดที่ประมาณ 200 ตัวอักษร** ตั้งแต่ต้นทาง (80% ของแถว ลงท้ายด้วย `... More`)
สคริปต์ตัดคำว่า More ออกแล้วใส่ `…` แทน ใจความหลักยังครบ

**ระดับ `Unknown` มี 28%** ในไฟล์ drug-drug ซึ่งไม่มีใน enum สคริปต์กรองทิ้งให้แล้ว

**ชื่อยาใช้แบบอเมริกัน** ไม่มี `Paracetamol` มีแต่ `Acetaminophen`
และไม่มี `Aspirin` มีแต่ `Acetylsalicylic acid`
→ ต้องทำตารางชื่อพ้องก่อนเปิดใช้ fuzzy search ไม่งั้นผู้ใช้ไทยค้นไม่เจอ

**หมวดอาหารเดิม 10 หมวดที่ตั้งไว้ก่อนเห็นข้อมูล ไม่ตรงกับของจริง**
แทนที่ด้วย 17 หมวดที่สร้างจากชื่ออาหารจริงทั้ง 29 ชื่อ โดย 2 หมวด
(`with_food`, `smoking`) ตั้ง `selectable = false` เพราะไม่ใช่ชนิดอาหารที่ผู้ใช้ติ๊กในไดอารี่

## การคัดยาสำหรับแอป

ชุดข้อมูล DDInter มียา **726 ตัว** ซึ่งส่วนใหญ่เป็นยาเฉพาะทาง เช่น ยาเคมีบำบัด
ที่กลุ่มเป้าหมายไม่มีทางได้ใช้ จึงคัดเหลือ **61 ตัว** ที่หาซื้อได้ในไทย
หรือใช้รักษาโรคที่พบบ่อย (รายชื่ออยู่ใน `CURATED_DRUGS` ของ `build_seed.py`)

ผลที่ได้
- ไฟล์ SQL เล็กลงจาก 1.8MB เหลือ ~100KB วางใน SQL Editor ได้ในครั้งเดียว
- **แปลไทยได้ครบ 100%** (จากเดิม 48%)
- ผลค้นหาสะอาด ไม่มียาเฉพาะทางที่ผู้ใช้ไม่รู้จักมาปน

เพิ่มยาได้โดยเติมชื่อใน `CURATED_DRUGS` แล้วรัน `python build_seed.py` ใหม่
ชื่อที่ไม่มีในชุดข้อมูลจะถูกข้ามไปเองพร้อมแจ้งเตือน

## สถานะคำแปลไทย

**แปลครบ 100%** ทั้ง 81 แถวของชุดยาที่คัดไว้

schema ยังรองรับกรณีที่ยังไม่มีคำแปลอยู่ (`mechanism_th` เป็น null ได้
แล้วแอปจะแสดง `description_en` แทน) เผื่อทีมเพิ่มยาใหม่ที่ยังไม่ได้แปล

**วิธีเติมคำแปล**: เพิ่ม key ใน `THAI_TEXTS` ของ `build_seed.py`
(key คือ 56 ตัวอักษรแรกของ Description ต้นฉบับ) แล้วรัน `python build_seed.py` ใหม่

## จุดที่ควรรู้ก่อนแก้ schema

**ชื่อยาไม่แปลเป็นไทย** — `drug_reference.name_en` เก็บชื่อสามัญภาษาอังกฤษตามมาตรฐานสากล
ส่วนที่แสดงเป็นไทยคือ `category_th` เช่นแสดงผลว่า `Paracetamol — ยาแก้ปวด / ลดไข้`

**`medications.food_risk_codes` เป็นข้อมูลที่คัดลอกมา ไม่ใช่ join สด** — คัดลอกจากตารางอ้างอิง
ตอนเพิ่มยา ทำให้หน้ารายละเอียดยาแสดงผลได้เร็วและใช้งานออฟไลน์ได้
แต่ถ้าทีมแก้ข้อมูลอ้างอิงภายหลัง ยาที่ผู้ใช้เพิ่มไปแล้วจะไม่อัปเดตเอง
จึงต้องมีปุ่มซิงค์ข้อมูลอ้างอิงใหม่ในหน้าตั้งค่า

**คู่ยาต้องเรียงจากน้อยไปมากเสมอ** — `drug_drug_interactions` มี constraint บังคับ
`drug_a_id < drug_b_id` เพื่อกันไม่ให้เก็บ (A,B) และ (B,A) เป็นคนละแถว
ตอน import ต้องสลับให้ถูกลำดับก่อน ไม่งั้นจะติด constraint

**RPC function ไม่ใช้ `security definer` โดยตั้งใจ** — เพราะ function ที่อ่าน `medications`
ต้องถูกกรองด้วย RLS ของผู้เรียกเอง ถ้าใส่ `security definer` จะข้าม RLS ทั้งหมด
กลายเป็นช่องโหว่ให้เห็นข้อมูลของบัญชีอื่น

**`dose_logs` unique constraint ไม่ครอบคลุมกรณี `medication_id` เป็น null** —
เพราะ Postgres ถือว่า null แต่ละค่าไม่เท่ากัน กรณีนี้เกิดเฉพาะตอนผู้ใช้ลบยาไปแล้ว
ซึ่ง log เดิมถูกสร้างไว้ก่อนหน้าแล้ว จึงไม่กระทบการใช้งานจริง

**`dose_logs` มี trigger กรองแถวทิ้งเงียบ ๆ** (`dose_logs_skip_cleared` จาก migrate-05) —
insert ที่ `source` ไม่ใช่ `manual` และ `scheduled_at` ก่อน `user_settings.history_cleared_at`
จะถูกข้ามโดยไม่ขึ้น error เพื่อไม่ให้ประวัติที่ผู้ใช้ล้างไปแล้วกลับขึ้นมา
ถ้าใส่ข้อมูลทดสอบแล้วแถวหายไป ให้เช็คตาราง `user_settings` ของบัญชีนั้นก่อน
(`seed-demo-account.sql` ล้างค่านี้ให้เองแล้ว)

## RPC function ที่มีให้

| function | ใช้ตอนไหน |
|---|---|
| `search_drugs(q, max_results)` | ผู้ใช้พิมพ์ชื่อยาในฟอร์ม → แสดงรายการชื่อใกล้เคียง |
| `check_drug_drug(p_drug_id)` | ก่อนบันทึกยาตัวใหม่ → เตือนถ้าตีกับยาที่กินอยู่ |
| `check_meal_interactions(p_food_codes)` | บันทึกมื้ออาหาร → เตือนถ้าหมวดอาหารตีกับยาที่กินอยู่ |

## ต้องทดสอบ RLS ด้วยมือก่อนส่งงาน

RLS ที่ syntax ถูกแต่ logic ผิดจะไม่มี error ให้เห็น ต้องทดสอบเองว่า

1. สมัครบัญชี A เพิ่มยา 1 รายการ
2. สมัครบัญชี B แล้วลองดึงข้อมูลยาทั้งหมด
3. บัญชี B **ต้องไม่เห็น**ข้อมูลของบัญชี A

ถ้าบัญชี B เห็นข้อมูลของ A แปลว่า RLS ยังไม่ทำงาน ห้ามส่งงานในสถานะนี้
